## P0 — Critical (fix this sprint) · 17 findings

### 1. `DF062` — ENV self-reference (4 services) [ERROR]
`ENV BUILD_NUMBER=${BUILD_NUMBER}` resolves to empty at build time, so the
intended build number is lost. Either drop the ENV line or feed it from an
ARG.
- **Files**: `automation/account_clone/Dockerfile:16`, `automation/automation/Dockerfile:7`, `base/Dockerfile:7`, `batchuser/Dockerfile:?`
- **Services**: `automation/account_clone`, `automation/automation`, `base`, `batchuser`
- **Fix**: `ARG BUILD_NUMBER=dev` then `ENV BUILD_NUMBER=$BUILD_NUMBER`

### 2. `DF015` — `apt-get install` without `-y` (1) [ERROR]
Build will hang on the first interactive prompt, depending on package set.
- **File**: `analyticsmigration/Dockerfile:24`
- **Service**: `analyticsmigration`
- **Fix**: add `-y` flag.

### 3. `DF002` — Explicit `USER root` (1) [ERROR]
Hard-codes container to run as root.
- **File**: `admin/Dockerfile-job:5`
- **Service**: `admin` (job variant)
- **Fix**: drop `USER root` and use the non-root user from the base image, or
  a dedicated UID for this job.

### 4. `DF020` — No `USER` instruction → defaults to root (10) [WARN, treated P0]
These containers run as root in production. Especially worrying for the
**gateway** family which is the public ingress.
- **Services**: `admin`, `gateway`, `gateway/analytics`, `gateway/case`,
  `gateway/integration-local` (×2), `gateway/lcnc` (×2), `gateway/mock`,
  `gateway/process`
- **Fix**: add a non-root `USER` after the package install layer in each
  gateway Dockerfile.

### 5. `DF010` — `sudo` inside container (2) [WARN, treated P0]
sudo inside an image is almost always a privilege-escalation footgun.
- **File**: `admin/Dockerfile` (×2)
- **Service**: `admin`
- **Fix**: drop sudo; do whatever it's wrapping in the right user context.

## P1 — High (next 1–2 sprints) · 137 findings

### 6. `DF001` — Unpinned `:latest` base image (59) [WARN]
Almost the entire fleet pulls `kissflow/base${BASE_IMAGE_VERSION}:latest`.
The ARG only controls the *image name*, not the *tag* — so every build
silently pulls whatever happens to be tagged `latest`. This is the biggest
supply-chain risk in the report.
- **Services**: 56 of 61 (every service except a handful of gateway variants)
- **Fix**: change the ARG to also pin a digest or version tag, e.g.
  `FROM kissflow/base:${BASE_IMAGE_VERSION}` + immutable tag policy in CI.

### 7. `DF064` — `useradd` without `-l` (50) [WARN]
With high UIDs (the base image uses UID > 100k), `useradd` initialises
`/var/log/lastlog` as a sparse file that can balloon image size by GB on
some filesystems.
- **Services**: 50 of 61 (every service that creates a user)
- **Fix**: pass `-l` (or `--no-log-init`). One-line patch in the shared
  base; ideally fix in `kissflow/base` once and rebuild children.

### 8. `DF004` — `apt` cache not cleaned (10) [WARN]
Adds tens of MB per service to the image layer.
- **Services**: `admin`, `analyticsmigration`, `automation/account_clone`,
  `automation/mongo_backup`, `externalconnection`
- **Fix**: append `&& rm -rf /var/lib/apt/lists/*` in the same `RUN`.

### 9. `DF036` — No `CMD` or `ENTRYPOINT` (5) [WARN]
Container has no default command — fine for *base* / *template* files,
broken otherwise.
- **Services**: `admin`, `analyticsmigration`, `automation/account_clone`,
  `automation/automation`, `base`
- **Triage**: confirm `base/Dockerfile` is meant to be a base image (likely
  fine); the others probably need a real entrypoint.

### 10. `DF057` — Pipe in `RUN` without `set -o pipefail` (5) [WARN]
A failure in the middle of a pipeline is silently swallowed, so a broken
download still produces a "successful" image.
- **Services**: `admin` (×3), `automation/account_clone`, `externalconnection`
- **Fix**: add `SHELL ["/bin/bash", "-o", "pipefail", "-c"]` near the top.

### 11. `DF003` — Too many separate `RUN` layers (4) [WARN]
Six consecutive RUN instructions where one would do — pointless layers,
slower builds.
- **Services**: `admin`, `automation/account_clone`,
  `automation/mongo_backup`, `externalconnection`
- **Fix**: collapse into one `RUN ... && ... && ...`.

### 12. `DF028` — `apt-get update` in a separate RUN from `install` (3) [WARN]
Causes cache poisoning: the install layer reuses a stale apt cache from a
previous build and pulls outdated packages.
- **Services**: `automation/account_clone`, `automation/mongo_backup`,
  `externalconnection`
- **Fix**: combine `apt-get update && apt-get install -y --no-install-recommends ... && rm -rf /var/lib/apt/lists/*` in one RUN.

### 13. `DF051` — `pip install` without version pins (2) [WARN]
Reproducibility hole — the same Dockerfile produces different bytes on
different days.
- **Services**: `apidocs`, `automation/mongo_backup`
- **Fix**: use a `requirements.txt` with pinned versions, or `pip install foo==1.2.3`.

### 14. `DF007` — `COPY . .` copies the entire build context (1) [WARN]
Risk of leaking `.git`, secrets, dev fixtures into the image.
- **Service**: `automation/mongo_backup`
- **Fix**: be explicit about what to copy *and* add a `.dockerignore`.

### 15. `DF011` — Single-stage build on a heavy base image (1) [WARN]
Ships build toolchain to prod.
- **Service**: `lowcode`
- **Fix**: split into a builder + runtime stage.

### 16. `DF049` — `COPY --from=<image>` references undefined stage (1) [WARN]
False positive — `COPY --from=ghcr.io/astral-sh/uv:0.9.8 /uv /usr/local/bin/uv`
is a valid pattern that copies from an external image, not a stage. Verify
once and **suppress with `--skip DF049`** in CI.
- **Service**: `base`

### 17. `DF058` — Both `wget` and `curl` used (1) [WARN]
Image carries two HTTP clients.
- **Service**: `admin`
- **Fix**: pick one.

## P2 — Recommendation (backlog) · 154 findings

### 18. `DF033` — Missing `.dockerignore` (60) [INFO]
60 of 61 service directories have no `.dockerignore`. Combined with `COPY .`
this is the leading cause of leaking dev junk into images. Cheapest
high-leverage fix in the whole report.
- **Action**: add a single shared `.dockerignore` template at the repo
  root and symlink / copy into each service.

### 19. `DF022` — No `EXPOSE` documented (47) [INFO]
Pure documentation issue — the gateway/route layer knows the ports anyway.
- **Action**: add `EXPOSE` to public-facing services as docs.

### 20. `DF016` / `DF005` — `apt-get install` without `--no-install-recommends` and without pinned versions (11 each) [INFO]
Same set of services that already need P1 cleanup. Fold into the same PR.
- **Services**: `admin`, `analyticsmigration`, `automation/account_clone`,
  `automation/mongo_backup`, `base`, `externalconnection`

### 21. `DF012` — No `HEALTHCHECK` (10) [INFO]
Mostly the **gateway** family + `lowcode`. Kubernetes liveness/readiness
probes already cover this in prod, so docker `HEALTHCHECK` is largely
cosmetic in our deployment — safe to suppress in CI for these services.
- **Services**: `gateway`, `gateway/*`, `lowcode`

### 22. `DF030` — `pip install` without `--no-cache-dir` (3) [INFO]
Wastes ~30–80 MB.
- **Services**: `apidocs`, `automation/mongo_backup`

### 23. `DF035` — `curl` without `--fail` (3) [INFO]
HTTP errors don't fail the build step.
- **Services**: `admin`, `externalconnection`

### 24. `DF056` — `wget` without `--progress=dot:giga` (2) [INFO]
Bloats build logs.
- **Service**: `admin`

### 25. `DF031` — `npm install` instead of `npm ci` (1) [INFO]
Reproducible builds.
- **Service**: `lowcode`
